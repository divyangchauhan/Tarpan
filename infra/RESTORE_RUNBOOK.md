# Backup & Restore Runbook (P6-05)

Operational procedures for the Tarpan RDS PostgreSQL database and the secret
rotation behaviour introduced in P6-04. Applies to the **prod** environment
(`cdk deploy --all --context env=prod`); the POC environment is disposable and
runs neither AWS Backup nor secret rotation.

---

## What protects the database

| Layer | Mechanism | Retention | Defined in |
| --- | --- | --- | --- |
| Built-in automated backups | RDS automated daily snapshots + transaction logs (enables point-in-time recovery) | 7 days (prod) | `database-stack.ts` (`backupRetention`) |
| Long-retention snapshots | AWS Backup plan, daily at 05:00 UTC | 35 days (prod) | `backup-stack.ts` |
| Stack-deletion safety net | `removalPolicy: SNAPSHOT` — final snapshot taken if the stack is destroyed | until manually deleted | `environment-config.ts` (`dbRemovalPolicy`) |

Point-in-time recovery (PITR) from automated backups gives the finest
granularity (any second within the retention window). AWS Backup recovery
points are the fallback for restores older than the automated-backup window or
if the RDS instance itself is lost.

---

## Restore procedures

> Restoring always creates a **new** RDS instance — you cannot restore in place.
> The application is then pointed at the new instance by updating the DB
> credentials secret and restarting the API.

### Option A — Point-in-time recovery (preferred, within 7 days)

```bash
# Restore to a timestamp (UTC). Omit --restore-time for "latest restorable".
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier tarpan-postgres \
  --target-db-instance-identifier tarpan-postgres-restore \
  --restore-time 2026-05-21T03:15:00Z \
  --db-subnet-group-name tarpan-db-subnet-group \
  --no-multi-az
```

### Option B — Restore from an AWS Backup recovery point (up to 35 days)

```bash
# 1. Find the recovery point ARN
aws backup list-recovery-points-by-backup-vault \
  --backup-vault-name tarpan-backup-vault \
  --query 'RecoveryPoints[].{Arn:RecoveryPointArn,Created:CreationDate}'

# 2. Start the restore (RDS metadata comes from the recovery point)
aws backup start-restore-job \
  --recovery-point-arn <RECOVERY_POINT_ARN> \
  --iam-role-arn <AWSBackupDefaultServiceRole ARN> \
  --resource-type RDS \
  --metadata '{"DBInstanceIdentifier":"tarpan-postgres-restore","DBSubnetGroupName":"tarpan-db-subnet-group"}'
```

### After either restore — cut the app over

1. Attach the same security group as the original instance so the API/Lambda can reach it:
   ```bash
   aws rds modify-db-instance --db-instance-identifier tarpan-postgres-restore \
     --vpc-security-group-ids <rdsSg id> --apply-immediately
   ```
2. Update the `tarpan/db-credentials` secret host/port to the restored endpoint
   (the username/password are preserved by the restore):
   ```bash
   aws secretsmanager get-secret-value --secret-id tarpan/db-credentials
   # edit host -> restored endpoint, then:
   aws secretsmanager put-secret-value --secret-id tarpan/db-credentials \
     --secret-string '{...updated json...}'
   ```
3. Force a new ECS deployment so API tasks read the updated secret:
   ```bash
   aws ecs update-service --cluster <cluster> --service <api service> --force-new-deployment
   ```
4. Verify `/health`, then rename/replace the old instance once confirmed healthy.

## Secret rotation (P6-04) — operational caveat

When `secretRotationEnabled` is true (prod), these secrets rotate every 30 days:

- **`tarpan/db-credentials`** — AWS-managed single-user rotation (configured in `database-stack.ts`).
- **`tarpan/jwt-secret`, `tarpan/jwt-refresh-secret`, `tarpan/internal-api-secret`** — regenerated by the custom Lambda in `infra/lib/lambda/secret-rotation/`.
- **`tarpan/anthropic-api-key`** — **not** rotated; its value is owned by Anthropic. Rotate it manually in the Anthropic console + `put-secret-value` when needed.

**The API and Lambda read secrets into environment variables at startup**, so a
rotation does **not** take effect until the consuming task/function restarts:

- After **DB credential** rotation, the single-user strategy changes the live
  password. Existing API tasks keep their old connection until they reconnect or
  restart; new connections with the stale password fail. Force an ECS
  redeployment after a rotation, or schedule rotations during a maintenance
  window. (A future hardening step is to have the API fetch DB credentials from
  Secrets Manager at runtime / on connection failure, or move to multi-user
  rotation.)
- After **JWT secret** rotation, all previously issued access/refresh tokens
  become invalid — users must log in again. This is expected; communicate the
  cadence or align rotation with a low-traffic window.
- After **internal API secret** rotation, both the API (ECS) and processor
  (Lambda) must pick up the new value. Redeploy the API and ensure the Lambda
  env is refreshed.

### Manually trigger a rotation (e.g. on suspected compromise)

```bash
aws secretsmanager rotate-secret --secret-id tarpan/jwt-secret
# then force the consumers to restart:
aws ecs update-service --cluster <cluster> --service <api service> --force-new-deployment
```
